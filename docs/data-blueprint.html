Verdict
Yes, for QLoRA tool SFT. Don't generate more yet.
  • The task is narrow: 12 tools, short commands, short replies. Each tool gets 1,000–1,650 calls. Papers that fine-tune small models for function calling see accuracy level off around 5–20K examples for a tool set this size.
  • LoRA only changes a small part of the model, so 20K examples is plenty for it. Too little data is not the risk here. The risk is the model memorising Gemini's phrasings. A held-out test set catches that.
  • Train on the text first. It costs about $2 and tells us whether the data works before we spend on turning it into speech.

Scope

What 20K commands can and can't teach

Teaches

  • Which tool to call, with which arguments
  • When to ask, refuse or just chat
  • Ordering for 2–3 step commands
  • Short spoken replies, which become Talker data later

Needs other data

  • Hearing: the audio adapter first learns speech from LibriSpeech (stage 1b)
  • Voice robustness: each command spoken in 3 TTS voices plus noise gives about 59K clips
  • Real voices: SLURP clips mapped to our tools
  • Seeing: LLaVA data (stage 1a and 2)
  • Not forgetting: 10–15% general chat replay

Run sheet

Blueprint, in order

Each step ends with a gate. Don't start the next step until the gate passes. Costs are Modal estimates at the plan's rates.

  1. Clean, normalise, split

    local CPU$0scripts/validate_commands.py
    • Validate every call against tools.yaml with jsonschema, apply the fixes above, and write a report.
    • Split by normalised utterance, stratified on category × tool: train ~18,150 · dev 500 · test 1,000.
    • Freeze the test set to data/splits/test.jsonl. It is never used for training or prompt tuning.
    GATE0 schema errors, report saved, splits share no utterance.

  2. Build the multi-turn samples in code

    local CPU$0src/services/data/synthetic_commands.py
    • Confirm: add yes and no follow-ups, with varied wordings ("yeah go ahead", "nah, leave it").
    • Weather: add a fake tool_response and a spoken summary ("It's 18 degrees and cloudy in Tokyo.").
    • Errors: add about 500 samples where a tool_response says it failed and the reply admits it ("Couldn't reach Spotify.").
    • Render everything with Qwen3's chat template: enable_thinking=False, tools as native <tool_call> JSON, loss on assistant tokens only.
    GATEPrint 20 rendered samples and check them by eye. Label mask covers assistant turns only.

  3. Text-only QLoRA, the cheap test

    A10G≈ $2–3apps/train.py::tools_text
    • First measure untrained Qwen3-0.6B on the test set. This is the baseline.
    • QLoRA settings: NF4 + double quant, r=32, α=64, dropout 0.05, all linear layers, LR 2e-4 cosine, 3% warmup, effective batch 64, max length 512, 3 epochs (about 900 steps).
    • System prompt holds a compact tool list (about 250 tokens), so new tools can be added later without retraining from scratch.
    GATEExact match (name + args) ≥ 90% on test, refuse/clarify accuracy ≥ 85%, and a clear jump over the baseline. If it falls short, fix the data before spending on audio.

  4. Turn commands into speech

    L40S≈ $12apps/synth.py
    • Speak each train/dev utterance in 3 random TTS voices (Kokoro first, licence checked). Add a random speed of 0.9–1.1× and background noise at 5–25 dB SNR.
    • Speak test utterances in a voice that is not used for training, so the test measures generalisation.
    • Map SLURP intents to our tools (music → media_control, volume, alarm → set_timer, weather) for real human audio.
    GATEWhisper-small transcribes a random 200 clips with WER under 8%. If it can't, the clip is bad.

  5. Teach the ears (stage 1b alignment)

    H100≈ $20configs/stages/1b_audio.yaml
    • Qwen3 is 4-bit and frozen. Only the audio adapter trains, on LibriSpeech plus SLURP transcripts with the prompt "Transcribe the audio."
    • This step must come before step 6. Otherwise the adapter learns "audio means some tool" instead of actually hearing the words.
    GATELibriSpeech test-clean WER is logged and falling. Overfitting 10 samples gets loss near 0.

  6. Spoken tool SFT (stage 3)

    H100≈ $16configs/stages/3_tools.yaml
    • Train the LoRA from step 3 plus the audio adapter. Mix: 60% spoken commands, 25% the same commands as text, 15% general chat and caption replay.
    • Train one epoch over about 59K clips. The text model already knows the tools, so this step teaches it to understand them when heard.
    GATESpoken exact match within 5 points of the text score from step 3. SLURP mapped-intent accuracy reported. MMLU subset drops by no more than 3 points.

  7. Merge, 8-bit, re-test

    H100≈ $8
    • Merge the LoRA into bf16 Qwen3, then load it in 8-bit. Adapters stay bf16. Run the whole test table again for 4-bit+LoRA, merged bf16 and merged 8-bit.
    GATE8-bit loses no more than 1 point of exact match compared with bf16.

  8. Reuse the replies for the Talker

    P5already in your data
    • The 13,234 distinct replies plus the weather and confirm templates become the Talker's speech data, in one fixed voice. You don't need a new Gemini run for this.
